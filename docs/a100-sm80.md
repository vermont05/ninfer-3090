# NInfer on an A100 (sm_80): build, run, measurements

v0.18.0-rtx3090 builds and runs unmodified on an **NVIDIA A100-SXM4-80GB** (GA100, sm_80, the same chip family as
the CMP 170HX that `CMakeLists.txt` already admits with `CMAKE_CUDA_ARCHITECTURES=80`). Tested on Google Colab
(Ubuntu 24.04, CUDA 13.0, gcc 13.3, 6 cores), 2026-11-15.

## Build

```bash
cmake -S . -B build-sm80 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_C_COMPILER=gcc -DCMAKE_CXX_COMPILER=g++ \
  -DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc -DCMAKE_CUDA_HOST_COMPILER=g++ \
  -DCMAKE_CUDA_ARCHITECTURES=80 -DNINFER_BUILD_APPS=ON -DBUILD_TESTING=OFF -DNINFER_BUILD_BENCHMARKS=OFF
cmake --build build-sm80 --parallel 12      # 677 objects, ~20 min on 6 cores
```

The binaries link only the CUDA 13 runtime, cuBLAS/cuBLASLt and the driver (all on the Colab image).

## Serve (Qwen3.8-27B, 8 lanes)

```bash
ninfer-serve qwen3_8_27b.ninfer --host 127.0.0.1 --port 8082 \
  --max-concurrency 8 --max-context 262144 --kv-capacity auto --max-pending-requests 32 \
  --kv-dtype rk4v4 --embedding-q4 --lm-head-q6 --gdn-state-fp16 --spec mtp --draft-tokens 3 \
  --prefill-cublas --prefill-chunk 4096 --host-context-mib 32768 --vision --vision-residency overlay
```

`--kv-capacity auto` gives a ~3.3M-token rk4v4 pool on 80 GB. Without `--vision`, an agent that reads an image gets
HTTP 400 "Vision is disabled" and Claude Code exits.

## Measured (stock `qwen3_8_27b.ninfer`, WarlaxZ/Qwen3.8-27B-NInfer-3090 @ d47f273)

| | A100 80 GB | RTX 3090 (this fork's docs / v0.16 in daily use) |
|---|---|---|
| Prefill, one 35k-token prompt | 3.85k tok/s | ~1.2-1.3k tok/s |
| Decode, one request (prose, MTP3) | 117 tok/s | ~80-97 tok/s |
| Claude Code agent swarm, 1 / 4 / 8 agents (aggregate output) | 51 / 290 / 360 tok/s | 83 / 117 / 143 (1 / 2 / 4) |

Swarm = N concurrent `claude -p` agents, each building a small Python project with tests, through ninfer's
`/v1/messages`; tokens from the proxy's per-request log.

## 16 lanes (branch `a100-16-lanes`, experimental)

`--max-concurrency` is capped at 8. Raising it to 16 needed: `kMaximumConcurrency`; ~25 kernel/plan admission
checks of `batch > 8`; the GDN replay row array (`GdnReplayFoldKernelRows::row[8]`: overflowing it crashed with
"stack smashing detected") and its 128-byte `static_assert`; `kMaximumRecordCapacity`; and the cuBLAS prefill
width gate (`kCublasPrefillMinTokens` 129 -> 257, so a 16 x 16-wide decode/verify round stays below it).
Result: correct (16 concurrent greedy requests, 16/16 exact answers, no crash over a 36-agent run) but **slower**:
8 / 12 / 16 agents = 360 / 259 / 294 tok/s aggregate. The kernels' tuned schedules stop at 8 columns per sequence
batch, so 8 lanes stays the right setting on this card.
